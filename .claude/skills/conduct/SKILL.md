# conduct — 指揮の案内役

利用者は非エンジニア。関わるのは **人の確認点** の3回だけ（最初の会話・途中確認・最終確認）。
作りたいものは、それまでの会話で固まっている。この案内役は、その後の全段階を人の操作なしで進める。
全段階をこの会話の Claude が自分で担当する。確認だけは、書いた本人の思い込みを持ち込まないよう、
新しい下請け（サブエージェント）に別々に行わせる。

## 絶対規則

- **時刻を決めた見回りを予約しない。** 利用者の返事待ち、自動チェック待ちの間も、`send_later`・
  `create_trigger`・`/loop`・`ScheduleWakeup` は使わない。返事や知らせが届いたときに動けば足りる。
- **利用者に途中で選択を求めない。** 下の各段階で使う部品（`/to-spec`・`/to-tickets` など）には
  利用者に確かめる手順があるが、利用者は人の確認点以外の判断を任せている。ここでは自分で決めて進め、
  決めた内容は計画書・作業指示に残す。
- **mattpocock/skills 由来の部品は書き換えない。** 中身を読んで、その手順に従うだけにする
  （利用者専用の部品は呼び出せないため、`.claude/skills/<名前>/SKILL.md` を読んで同じことをする）。
- 決めた理由（`docs/adr/`）があれば、確認役に渡す依頼文に**そのまま貼り付ける**。食い違いは違反として扱わせる。
- 利用者への報告はすべて `docs/agents/flow-map.md`「説明の書き方」の3ブロック（結論／理由／次）で書く。

## 確認役（下請け）への頼み方

確認役は、この会話を知らない新しい下請けとして起こす。依頼文には、目的、読むべき文書
（計画書・作業指示の本文、決めた理由を貼る）、やってほしいこと、返してほしい形を必ず含める。
2人に頼むときは**別々に**起こし、互いの答えは見せない。

## 手順

### 0. 始める前に

1. 作業用の枝を用意する。作業環境が使う枝を指定していればそれを使い、無ければ本流の最新から
   `conduct/<短い英語の名前>` を作る。以降の記録はすべてこの枝に送る。最初に送ったときに、
   この枝の提出物を**下書き**として作る（最終確認の GO で本流へ取り込む対象になる）。
2. 3ブロックで始めることを伝える（**次**: 「次に声をかけるのは途中確認のときです。」）。

### 1. 用語と決定の記録

`.claude/skills/domain-modeling/SKILL.md` を読み、会話で決まった用語を `CONTEXT.md` に、
後から覆すと高くつく判断を `docs/adr/` に書き残す。記録すべきものが無ければ何も作らない。

### 2. 計画書

`.claude/skills/to-spec/SKILL.md` を読み、その手順で計画書を書いて作業指示として登録する。
検査の入口の確認は利用者に聞かず、自分で決めて計画書に書く。

### 3. 設計の確認

計画書の本文を渡し、確認役2人に**別々に**確認させる。依頼文には「抜け・矛盾・危険・もっと単純な案」を
挙げるよう書く。2つの答えを踏まえて計画書を直し、直した計画書で作業指示を更新する。

### 4. 小分け

`.claude/skills/to-tickets/SKILL.md` を読み、その手順で作業指示に小分けして登録する。
分け方の確認は利用者に聞かず、自分で決める。

### 5. 実装

先に済ませる作業が無いものから順に、1件ずつ進める。

1. `.claude/skills/tdd/SKILL.md` の手順で、先に失敗する検査を書き、通す。
2. 検査を流す。落ちていれば原因を直して流し直す。
3. 通ったら作業用の枝に記録して送る。作業指示を閉じる。

最初に「動くもの」が1つできた時点で、**6. 途中確認**を挟む。

### 6. 途中確認（人の確認点）

最初に、利用者が触って意味のある「動くもの」ができたら1回だけ行う。

1. `run` の部品で起動し、動いている様子の画面写真を撮る。作るものによっては、触れる画面へのリンクも用意する。
2. 利用者に送る中身は次の2つだけにする。
   - 3ブロックの説明。専門用語は使わない
     - **結論**: 何ができたか
     - **理由**: どう動くか（画面写真のどこを見ればよいか）
     - **次**: 「このまま進めてよければ GO、違えば NG と一言の理由をお返しください。」
   - 画面写真（会話に添付する）。あればリンク
3. 送ったら**止まる**。
4. GO なら 5. 実装に戻る。NG なら、理由を作業指示に書き足して直し、もう一度 6. 途中確認をやり直す。

### 7. 仕上げの確認

全作業指示が閉じたら、`.claude/skills/code-review/SKILL.md` の手順で、本流との差分全体を
計画書と照らして確認する（決めた理由は `docs/agents/flow-map.md` の規則どおり確認役に貼る）。
指摘には重さ（直さないと出せない／直した方がよい／好み）を付けさせる。

### 8. 修正

仕上げの確認の指摘のうち、「直さないと出せない」「直した方がよい」を直す。
直したら検査を流し、記録して送る。設計の変更をした場合は 7. 仕上げの確認をもう一度行う。

### 9. 最終確認（人の確認点）

6. 途中確認と同じ形（3ブロックの説明＋画面写真、あればリンク）で、完成したものを送って**止まる**。

- **GO**: 作業用の枝の提出物を下書きから正式な提出に切り替え、自動チェックが通っていることを確かめてから
  本流へ取り込む（`gh` が無ければ GitHub の MCP ツールで同じことをする）。自動チェックが落ちていれば直してから
  取り込む。取り込めたら3ブロックで伝え、引き継ぎメモに記録する。
- **NG**: 一言の理由を作業指示にして 5. 実装から直し、7. 仕上げの確認を経て、もう一度最終確認を行う。

## 記録

- 計画書の登録後、小分けの登録後、途中確認の GO 後、最終確認の GO 後に、引き継ぎメモへ1件ずつ足す
  （書式は `docs/agents/flow-map.md`「引き継ぎメモ」）。
- 「次にやること」には、どの段階のどの作業指示から再開するかを書く。
